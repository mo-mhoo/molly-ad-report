2026-08-19，[[project_meta_cpas_app_dev_mode_blocker]] 這個案例裡，連續 3 次 session（含這次一開始）都只是複述 2026-08-05 那次 session 的結論「來源貼文由開發模式 App 建立、工具端無法繞過，需要去 App 後台切 Live」，沒有人回頭實測「是不是真的無法繞過」。這次因為 Molly 帶回另一邊 claude chat（官方 Meta Ads MCP）的做法（直接重用既有 creative_id 建新廣告，完全不建新 creative），才發現其實有辦法繞過——根因也被推翻重新診斷（不是「來源貼文的 App」有問題，是我們自己這組 token 背後的 App `tsa000(M)` 在開發模式，任何建新 creative 的動作都會被擋，但重用既有 creative_id 不會觸發這個檢查）。

**Why**：Molly 明確點出這是「定錨」（anchoring）——一旦前面的 session 已經下了「無法解決/工具端擋死」這種終結性結論，後面的 session 容易直接採信、不再往下追問，尤其是這類結論讀起來很像「已經徹底診斷過的死路」。但實際上前面的診斷可能只測過一兩種做法，沒有窮盡所有 API 路徑。

**How to apply**：
- 遇到記憶或過去 session 裡標注「無法解決」「工具端無法繞過」「平台限制」這類終結性診斷時，把它當成**待驗證的假設**，不要直接照搬答案給用戶當結論。
- 尤其是牽涉多種可行 API/實作路徑的問題（例如 Graph API 同一個目標常有好幾種呼叫方式），過去的診斷可能只測過其中一兩種，不代表窮盡了所有選項。
- 如果情況允許（有測試環境、寫入是可逆的如 PAUSED 廣告），優先自己動手做最小可行測試去確認，而不是只憑過去結論回答「做不到」。
- 這不代表每次都要重新從零開始懷疑一切——已經反覆驗證過、有明確技術原因支撐的結論（例如帳戶權限類）可以沿用；真正該提高警覺的是「宣告某條路徹底走不通」這種一次性診斷、且沒人真的窮盡過替代方案的情況。
