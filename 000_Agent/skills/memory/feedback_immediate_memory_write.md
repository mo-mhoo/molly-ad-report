Molly 2026-09-11 直接點出：「有更新或修復為什麼不筆記」「重複犯錯的意義是？」——這不是單一次疏漏，是一個系統性習慣問題：debug/修復當下忙著把眼前的問題解決、驗證、回報結果，很容易忘記在收尾前補寫記憶，或想著「等這輪任務全部做完再一起補」，結果任務一多、對話一長就真的忘記，或者被中間插進來的新問題打斷。

**這次的具體案例**：Molly 給我看另一個 session 修好 momo TOP3 魚油5入 Canvas 廣告 creative 結構的截圖（`product_set_id`／`retailer_item_ids`／`post_click_configuration` 三欄位到位，格式才會正確顯示精選集），問我「你有記下來嗎」——查了才發現沒有，這個具體修復知識只存在那次對話的截圖裡，沒有進到 [[project_meta_ad_video_img_upload_skill]]。緊接著她又說「我剛剛叫另一個session跑skill居然又出錯」——這正是記憶沒寫、知識沒傳遞的直接後果：不同 session/裝置間如果沒有共享記憶，同一個坑會被踩好幾次，即使 [[feedback_git_sync_setup_2026_09_11]] 已經把 git 同步修好，「有沒有東西可以同步」跟「修完當下有沒有寫下來」是兩個獨立的問題，同步修好了但沒寫的東西還是不存在。

**Why 這條要獨立成一則記憶，而不是只靠 CLAUDE.md 既有的「Session 進行中立即寫入 MEMORY.md」規則**：因為那條規則顯然沒有被穩定執行——寫成通用指示型的規則容易在忙碌時被忽略，需要一個具體、可以被指出來的失敗案例當提醒，讓「這條規則真的很重要」這件事更難被輕易略過。

**How to apply**：
1. 任何一次 debug／踩坑／收到 Molly 糾正／確認某個做法有效之後，**在繼續下一步之前**（不是等這輪任務全部結束），先問自己一句：「這件事下次還會用到嗎？如果不記下來，下一個 session 或下一次任務會不會重複踩同樣的坑？」，是的話立刻寫，不要排到後面。
2. 特別容易漏記的情境：debug 過程中反覆試錯、最後才成功的（因為專注力都在「終於成功了」，容易直接跳到回報結果，忘記回頭把「怎麼修好的」寫下來）——這正是這次 momo Canvas 案例的模式。
3. 如果一次任務裡有好幾個值得記錄的點，可以先用簡短文字條列到 scratchpad，任務中段找空檔就先寫成正式記憶檔，不要全部堆到最後才一次補（越堆越容易漏、細節也會記不清楚）。
4. 這條本身也要定期回頭檢查有沒有被確實執行——如果之後又發生「這件事沒寫記憶」的情況，代表這條記憶本身也需要被加強或换個方式提醒。
